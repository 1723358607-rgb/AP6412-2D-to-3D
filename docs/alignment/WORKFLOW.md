# 逐步开发、可复制指令与验收 v1.0

实施更新 v1.1：用户指定 Godot Mono/.NET 和 C#；A 本机已检测4.7.2 Mono与.NET SDK10.0.302。所有任务使用 C#、公共基类及 CONTRACT 的 PascalCase 接口；不要使用旧 GDScript 示例。第0步本机自动检查与未完成验收见 docs/evidence/member-a/step-0.md。

身份映射：A=用户的队友（玩法），B=当前用户（UI/视觉/进度）。早期版本曾把两个人写反，但 A/B 的模块职责和第 0—7 步计划不变。详见 [MEMBER_ATTRIBUTION.md](MEMBER_ATTRIBUTION.md)。不要求学生手写代码；要求学生实际检查、提出修正并理解自己的模块。

## 每轮指令都加上的公共要求

> 先读取 docs/alignment/README.md、SPEC.md、CONTRACT.md 和本步骤。检查真实仓库当前状态、分支与未提交修改；不要覆盖他人工作。只在本人个人分支开发。说明文件范围，遵循公共接口和文件归属。完成后运行相关检查，分别列明通过、失败、未执行；给我普通玩家能操作的手动验收步骤。只提交自己的工作，保留有意义的提交和 PR/merge 历史。无法访问仓库、Godot 或运行环境时如实说明，不宣称已完成或测试通过。完整原始 AI 对话与价值索引分别保存；不能把摘要冒充完整日志。

下面的提示词与公共要求一起使用。每步做完、验收后再进入依赖它的下一步。

## 第 0 步：共同工程和连接骨架

### A 发给自己的 AI

> 执行第 0 步。我负责玩法，使用 member-a。先确认本机 Godot 完整版本和队友使用版本的一致性；若队友版本未知，记录待确认，不擅自选择不同版本。读取仓库现状后，在 game/ 建立唯一 Godot 工程、基础忽略规则、目录与总入口骨架，预留 CONTRACT 中的 GameSession 和 UI 连接位置。此时不实现三消或 3D，不替队友编写整套 UI。写明打开/运行步骤与实际版本，提交可供队友同步的工程初始化。若本机没有 Godot，明确告诉我缺什么，先准备可审阅文件，不能宣称已运行。

### B 同时做什么

在独立工作副本同步已发布的对齐文档、确认账号/版本/分支；先理解页面流程。等 A 的公共工程合并后再在同一个 game/ 工程内写 UI；可以先画页面草图或整理 UI 验收，不创建第二个 project.godot。

### B 发给自己的 AI

> 我负责 UI，使用 member-b。读取对齐文档和仓库现状，检查能否访问并确认当前工程/接口。先回报我负责的页面、存档职责、文件边界和与玩法的连接方式。确认 Godot 版本；同步 A 已合并的共同工程后再开发 UI。若共同工程尚未就绪，先整理 UI 页面方案和验收，不创建另一套工程，不修改玩法或项目设置。

### 验收与连接门槛

- A：指定路径导入工程，运行时打开基础入口，无解析错误；记录实际运行结果。
- B：从自己的副本打开同一版本工程，能够运行；能指出自己的 UI 目录和个人分支。
- 共同：Godot 完整版本一致；main 中只有一个工程；双方读的是同一版本约定。

## 第 1 步：棋盘原型与页面原型并行

### A 指令

> 执行第 1 步，仅完成 2D 棋盘原型：7×7、四种颜色与形状、第一关固定木箱布局、点击选中和相邻交换请求。建立不依赖显示坐标的 BoardModel 和合法性判断；准备第一关确定性配置，不生成 3D。此时可以先不完成消除，但必须明确哪些仍是占位。不要实现队友的菜单/HUD。提供越界、木箱、非相邻请求被拒绝的检查结果，以及玩家手动检查步骤。

### B 指令

> 执行第 1 步。在 game/ui/ 实现开始、选关、游戏 HUD、胜利、失败、离开确认页面，并按 CONTRACT 发出请求。使用 game/tests/ui/ 下明确标注的模拟入口预览页面；测试快照必须符合协议，模拟数据不进入正式存档。先不连接真实三消，不写玩法或另一套 GameSession。记录页面场景路径和接口。

### 验收

- A：看到 49 格及正确木箱位置；四种棋子可区分；点击可选中；非相邻/木箱交换不会改坏数据。
- B：开始→选关→测试游戏→测试结算均可到达；三张卡片、0—3 星、锁定和最后关按钮状态可预览；离开取消回到当前测试局。
- 共同：提交各自改动，队友复核；记录实际使用的场景路径，第一次确认接口。

## 第 2 步：消除闭环与真实 HUD

### A 指令

> 执行第 2 步。实现有效交换、匹配去重、无效交换回退、一次扣步、下落补充与连锁，并由 GameSession 发布真实快照。动画期间锁定输入。先使用可控测试棋盘验证，不把测试板当作正式关卡。只让表现层显示核心计算的结果。记录一次无效交换、有效交换和连锁的前后数据及实际自动检查结果。

### B 指令

> 执行第 2 步。让游戏 HUD 接收 GameSession 的真实 snapshot，显示关卡名、剩余步数和木箱目标，支持启动时立即刷新。保留独立 UI 测试入口，但正式游戏界面不得继续使用假计数。请求 A 连接总入口，不自己重写消除规则或修改 GameSession。缺失字段列清后交给 A。

### 验收

- A：无效交换回退且不扣步；有效交换只扣一次；连续下落和连锁完成；快速连点不会重复结算。
- B：实际交换后 HUD 随真实数据变化；连锁不多扣步；新开局立即显示正确数据，无旧关残留。
- 共同：首次真实接线，消除不是仅在测试页面中成立；若目标逻辑未完成，明确标为待接入。

## 第 3 步：木箱、三关、星级和进度

### A 指令

> 执行第 3 步。按 SPEC 实现单/双层木箱、每轮最多一次伤害、区段下落、三关配置、结算与整数星级算法。全部连锁结束后先判胜再判失败；每局只发一次 result。补齐重试和离开取消旧会话。给出星级边界与最后一步通关的可复现验证，不为通过测试悄悄改规则或声称初始步数已平衡。

### B 指令

> 执行第 3 步。实现 ProgressStore，记录最高星数、通关解锁下一关、2D/3D 独立存档和重启读取。连接真实结算，区分本次星数与历史最佳；第三关不显示不存在的第四关。存档自动检查使用隔离文件。进度记录由总入口接线后，在选关重新进入时刷新，不在 UI 重新计算星级。

### 验收

- A：第一关双边界剩余2/3、5/6；第二关3/4、7/8；第三关4/5、9/10的星数正确。失败为0；最后一步完成为1；双层箱减一层时目标个数不减。
- B：拿到成绩后返回选关可见星数；三星后拿一星仍存三星；失败不覆盖；任意通关可解锁下一关；关闭重开保留；2D/3D 成绩不混用。
- 共同：完整走通开始→选关→游玩→结算→返回显示成绩；再走失败→重试。

## 第 4 步：完整 2D 跑测与修复

### A 指令

> 执行第 4 步。检查初始无匹配、至少有合法步；实现稳定盘面无合法步时的确定性重排；保护木箱、层数与步数。使用有界尝试与明确错误处理，避免生成死循环。跑测三关，记录种子和有效操作序列，评估初始步数与星级难度，再提出有证据的参数调整。覆盖重试/返回/快速点击等边界，不动队友文件。

### B 指令

> 执行第 4 步。检查所有真实页面路径、离开确认、重试、下一关、最终关、锁定卡片、进度读取和异常存档处理。检查目标清晰度、颜色/形状辨识与窗口内布局。用隔离存档复现，不清除真实成绩。把玩法侧问题写出复现步骤交给 A。

### 验收

- A：三关都有可复现的通关路径；失败能够复现；重排后可继续；没有无限结算/生成/点击竞争。
- B：每条按钮路径正确；离开取消不丢当前局；确认离开不会突然弹旧结算；重开不显示旧数；存档损坏不崩溃。
- 共同：两个人分别从 README 指定入口完整运行三关；记录通过、失败、未执行项目，不只写“都正常”。

## 第 5 步：冻结 2D 与保存证据

### A 指令

> 执行第 5 步。整理与实际代码一致的玩法类图、关键设计理由、已知限制、运行说明和真实验证记录。确认 UI 分支合并、工程无临时占位且两人运行检查通过后，冻结可运行 2D 基线，创建 2d-baseline 标签。条件未满足时列出缺项，不提前打完成标签；不移动既有标签。

### B 指令

> 执行第 5 步。整理 UI/ProgressStore 类图、页面流程、真实截图或操作证据、个人贡献和 AI 日志位置，检查最终 2D 工程与存档。从自己的干净工作副本验证 A 的运行说明。对待冻结提交给出具体复核结果；不编造评审或合并记录。

### 验收

- 标签对应的 2D 可独立获取并运行三关；所有 UI 是真实连接。
- 类图对应代码；个人分支和 PR/merge 历史可见；完整 AI 日志已定位，精选索引另存。
- 保存标签 SHA、引擎版本、关卡参数、种子与操作序列；从此不改旧标签。

## 第 6 步：3D 转换与 UI 复用

### A 指令

> 执行第 6 步，必须从已冻结 2D 基线继续。新增真正三维的棋盘、棋子与木箱、相机、点击映射和动画适配，复用核心规则、关卡与随机序列。不要创建另一套匹配/星级代码，不让物理决定下落。使用相同种子和合法操作序列，对比两版每步棋盘、步数、目标和结果。记录必要的实际核心改动，不为追求零 CCR 隐瞒变化。

### B 指令

> 执行第 6 步。把原有开始/选关/HUD/结算接入 3D 游戏，尽量复用相同 UI 场景和 ProgressStore；改为 progress_3d 独立存档。验证棋盘点击不会穿过 UI、相机不遮挡信息、3D 结算与历史星数正确。发现玩法映射错误交给 A。整理哪些 UI 文件未变，哪些因真实需求变更。

### 验收

- A：实际三维对象与选取工作；同种子同操作结果一致，或准确定位并修复差异；旧 2D 标签仍可运行。
- B：界面全过程可用，按钮不误触棋盘；两个版本存档独立；本次/最佳星级正确；窗口内无明显遮挡。
- 共同：三关 3D 可玩，不只是 3D 模型预览；保留真实版本差异与检查记录。

## 第 7 步：最终标签、报告与展示

### A 指令

> 执行第 7 步。检查已整合版本并完成3D最终类图、变更表和核心复用分析；与 B 明确 CCR 的核心类范围、公式、统计口径和新增/修改/删除数量，依据真实 Git 差异计算。完成运行说明和已知限制；两人验收后冻结 3d-final，保留 2d-baseline...3d-final 对比，不篡改旧历史。整理本人报告部分和个人反思素材，不代替他人虚构反思。

### B 指令

> 执行第 7 步。完成 UI/进度模块变更证据、存档与完整流程检查、报告 UI 部分和本人个人反思素材。与 A 检查一个 PDF 小组报告、每人具名反思、声明、AI 完整日志和所有 GitHub 链接。准备现场菜单/结算/历史星级演示，配合约15分钟双人展示，不用录屏替代实机。

### 验收

- 两个可运行版本、标签、版本对比、类图、变更表、CCR 计算口径齐全。
- 一份 PDF 报告包含每人独立反思；真实开发证据、完整 AI 对话位置、课程声明齐全。
- `AP6412_GroupXX.zip` 明确每个版本位置与运行方式；截止时间以 NTULearn 为准。
- 两人都能解释自己负责模块和至少一次 AI 建议的评估/修正过程。

## 每步提交与证据格式

各自记录到 `docs/evidence/member-a/step-N.md` 或 `docs/evidence/member-b/step-N.md`，避免同时编辑公共状态文件：

```text
步骤/负责人：
代码提交/PR：
Godot版本、系统和入口：
实际完成：
自动检查（命令、实际输出摘要、通过/失败/未执行）：
手动检查（操作、期望、实际）：
复现种子与操作序列：
已知问题/交给对方的依赖：
完整AI日志路径：
有价值对话索引：
下一步条件是否满足：
```

测试夹具/调试入口可以帮助复现极端情形，但须与正式游戏分开、明确标注；不能用强制胜利按钮充当正常可玩性证据。
