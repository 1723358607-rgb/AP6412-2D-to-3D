# 第5步设计理由与2D→3D对比准备

这是当前实现的解释与统计准备，不是最终报告、学生反思或冻结证明。日期：2026-11-09，新加坡。

| 设计 | 当前实现及理由 | 实际代价或边界 |
|---|---|---|
| 行列坐标表达规则 | GridPosition不引用Godot.Vector；2D与3D可发出相同SwapRequest | 3D拾取必须真实验证，换模型本身不能证明输入一致 |
| 不可变棋盘快照 | BoardModel拷贝输入和输出数组，BoardStep保存前后状态 | 每轮产生多个小数组；7×7和三关规模可接受 |
| 先算规则，再播放 | MatchResolver输出Swap/Clear/Fall/Refill/Reshuffle序列；IBoardPresenter只播放 | 会话须处理取消与播放失败回退；不能让物理自由落体改变补充顺序 |
| 随机流显式保存 | xorshift32使用uint；初始生成、补充、重排共享确定性状态 | 同色算法、遍历顺序或重排尝试改变都可能影响后续棋盘，需记录真实差异 |
| 木箱按轮去重 | ClearMatches收集相邻木箱集合，每轮最多减一层 | 同一有效交换的下一轮连锁可再减层；不是每次交换只减一层 |
| 先判胜后判失败 | LevelRules先检查剩余箱0，再检查剩余步0 | 最后一步胜利仍获1星；UI不得看中间target=0提前跳页 |
| 整数三星边界 | 剩余×5与初始/初始×2比较 | 关卡总步数改变会影响星界，本轮保持15/20/24 |
| 有界死局恢复 | 只洗牌现有普通棋子，固定箱位与层数；最多512次 | 无解时明确失败、不提交源事务；不宣称所有拓扑都可恢复 |
| 应用拥有棋盘 | AppController换页前ParkBoard，避免B销毁BoardHost时删掉棋盘 | 页面布局/事件穿透仍须真实UI联调，不是接口同名即可 |
| 职责分工 | A维护规则/会话/表现；B维护UI/存档；A临时应用适配器复用B页面 | 当前RAM进度不能冒充最终持久化；只增加存档空壳会切回未接完的B原UI |

## 已保存的对比证据

- `step-5-rule-reference.json`：3个开局、16次正式有效交换的稳定状态，以及实际IBoardPresenter消费的217个中间步骤。每步含7行棋盘、木箱层数、被清除/受伤格；稳定状态含剩余步数、目标、RNG和最终星数。
- 字母R/B/G/Y对应核心PieceColor，现用贴图实际是粉心/蓝滴/紫钻/金六边形；不能据字母误判美术颜色。1/2是箱层数，`.`为空位。
- 格子hash：7行ASCII用LF连接，无末尾LF，UTF-8后SHA256。JSON缩进不是格子hash输入。
- 本次原始输出重复两次完全一致；`tools/verify-2d-reference.py`逐项比较生成JSON与档案，默认拒绝差异，不自动覆盖参考。
- 当前是未冻结候选。正式2D冻结时若规则有变，需保留当前记录，另存最终版本，不能悄悄覆盖历史参考。

这些证据直接来自GameSession和RecordingPresenter，不是手写棋盘或只记录胜负。它们尚未验证3D显示、射线拾取、相机或鼠标UI遮挡；第6步必须用实际3D表现器做同序列比较。

## 变更统计准备（不预报CCR）

完整类型清单和源码SHA256见 `step-5-source-manifest.json`。当前纯core有9个文件、21个公开类型，不等同21个class。供双方讨论的业务规则范围为BoardModel、BoardGenerator、BoardMoves、MatchResolver、LevelRules、LevelDefinition、BoardInteraction；BoxDefinition和7个record为数据类型，6个enum为枚举。最终核心范围、是否含DTO、GameSession、统计公式和新增类口径须对照作业要求并在正式比较前写明。

不在3D尚未实现时计算“CCR=0”，也不把测试类、空3D骨架或重命名包装当核心复用证据。正式统计必须使用不可移动的2d-baseline与3d-final标签实际Git差异；目前两个标签都未创建。
